# Commerce ETL v0 — 프로젝트 설계와 진행 방향

> **여러 주문 파일을 병렬로 처리하면서, 실패한 작업을 다시 실행해도 최종 데이터가 정확하게 유지되는가?** 이 질문을 v1·v2·v3에 걸쳐 구현과 실험으로 확인한다.

이 글은 프로젝트의 목적과 버전별 진행 방향을 정리한 제안서다. 작성 시점에는 v1 구현·실행 검증을 마쳤으며, v2와 v3는 앞으로 진행할 계획이다. 세부 작업 체크리스트는 [PLAN.md](../PLAN.md)에 관리한다.

## 1. 어떤 프로젝트를 만들 것인가

쇼핑몰마다 다른 형식으로 전달하는 주문 파일을 공통 형식으로 바꾸고, 개인정보를 처리한 뒤 PostgreSQL에 적재하는 배치 파이프라인을 만든다.

```text
쇼핑몰 A의 주문 CSV + 쇼핑몰 B의 주문 JSON
    ↓
입력 파일 목록 확정·원본 보관
    ↓ Airflow에서 파일별 병렬 처리
    ├─ 파일 A → 검증·표준화·가명화 → 결과 파일·DB 적재
    ├─ 파일 B → 검증·표준화·가명화 → 결과 파일·DB 적재
    └─ 파일 C → 검증·표준화·가명화 → 결과 파일·DB 적재
    ↓
주문별 처리 결과 집계 → 누락·중복·내용 검증
```

v1에서 연결한 기본 흐름이다. 입력은 외부 쇼핑몰 API가 아니라 직접 생성한 합성 파일이며, 운영자가 DAG를 실행하면 내부 처리가 자동으로 진행된다.

실무에서는 의료영상 ETL을 개발했다. 여기서는 서로 다른 입력 형식, 개인정보 처리, 병렬 적재, 재처리라는 문제를 평가자가 이해하기 쉬운 주문 데이터로 재구성한다. 회사 데이터나 운영 코드를 공개하는 프로젝트가 아니며, 공개용 실험 결과와 회사에서의 실무 성과도 구분한다.

## 2. 단순히 데이터를 DB에 넣는 것에서 무엇을 더 보여줄 것인가

포트폴리오에서 설명할 문제는 세 가지로 좁힌다.

| 질문 | 확인할 내용 |
| --- | --- |
| 파일을 동시에 처리하면 무엇이 달라지는가? | 동시 실행 수 1·2·4에서 실제 실행 중첩과 처리량 변화 |
| 여러 파일 중 하나만 실패하면 어떻게 복구하는가? | 성공한 작업을 유지하고 실패한 태스크를 재시도·재실행 |
| 다시 실행하거나 같은 주문이 동시에 들어와도 안전한가? | 주문 키·금액·고객 토큰 유지, 중복과 내용 충돌 구분 |

예를 들어 A·B·C를 처리하다 B의 DB 적재만 실패했다고 가정한다. A·C까지 처음부터 다시 처리해야 하는지, B를 다시 실행하면 이미 저장한 주문이 중복되는지, 최종적으로 세 파일의 주문이 모두 반영됐는지를 설명할 수 있어야 한다. 이 상황은 v2에서 의도적으로 재현할 예정이다.

## 3. 왜 Airflow를 사용하는가

Airflow에는 **파일별 작업 생성, 동시 실행 수 제한, 태스크 의존성, 재시도와 실행 이력 관리**를 맡긴다. 데이터 변환과 중복 방지는 Python 코드와 PostgreSQL에서 처리한다.

입력 파일 개수에 따라 Dynamic Task Mapping으로 작업을 만들고, 전용 Pool로 동시에 실행할 파일 수를 제한한다. 한 주문마다 태스크를 만들지 않고 파일을 단위로 삼아 스케줄링과 재처리의 경계를 맞춘다.

| 구성 | 역할 |
| --- | --- |
| Airflow DAG·Pool | 파일별 실행 순서·병렬도·태스크 상태 관리 |
| Python ETL | 입력 형식 통일·값 검증·고객 정보 처리 |
| PostgreSQL | 주문 고유 키·트랜잭션·처리 이력 저장 |
| 공유 파일 볼륨 | 원본 사본·표준 파일·실행 보고서 보관 |
| Docker Compose | 외부 사내 시스템 없이 재현 가능한 실행 환경 |

실행 환경은 LocalExecutor를 사용하는 단일 머신이다. 여러 프로세스를 병렬로 실행하며, 여러 서버에 걸친 분산 처리까지 구현한 것으로 표현하지 않는다. Airflow 메타데이터와 주문 데이터도 별도 DB로 구분한다.

## 4. 버전별로 무엇을 완성할 것인가

| 버전 | 핵심 질문 | 주요 결과물 | 현재 상태 |
| --- | --- | --- | --- |
| **v1 · 병렬 ETL 기준선** | 서로 다른 파일을 병렬 처리하고 정확히 적재하는가? | 실행 가능한 DAG, 공통 주문 모델, 결과 검증 기록 | 구현·검증 완료 |
| **v2 · 실패와 재처리** | 중간 실패를 복구해도 중복·누락이 없는가? | 장애 주입 시나리오, 선택적 태스크 복구 데모, 재실행 테스트 | 계획 |
| **v3 · 성능과 정합성** | 적절한 병렬도는 무엇이며 저장 후 불일치도 찾는가? | 반복 측정 결과, 별도 정합성 검사 DAG, 최종 데모 | 계획 |

### v1 — 정상 처리와 병렬 실행의 기준선을 만든다

첫 버전은 처음부터 끝까지 실행되는 작은 파이프라인을 완성하는 단계다. 가상 쇼핑몰 A는 CSV, B는 JSON으로 입력하고, 두 형식을 같은 주문 모델로 변환한다.

주문은 `(source, order_id)`로 식별한다. 같은 키의 같은 내용은 중복으로 판정하고, 같은 키의 다른 내용은 충돌로 기록한다. 고객 ID는 안정적인 가명 토큰으로 바꾸고, 이름·이메일·주소는 분석 결과에서 제외한다.

```text
합성 파일 생성 → DAG 실행 → 파일별 병렬 적재
    ↓
같은 입력으로 DAG 재실행
    ↓
고유 주문 수·내용 유지 확인
```

**완료 기준:** 새 환경에서 Compose로 실행할 수 있고, Pool 1·2·4의 실제 처리 중첩과 적재 결과를 확인할 수 있다. 태스크 상태뿐 아니라 주문 키·내용·결과 파일을 대조한 기록을 남긴다.

**현재 확인한 결과:** 8파일·40,000주문을 적재했다. Pool 4·1·2 순서로 실행해 최대 처리 중첩 4·1·2를 확인했고, 재실행에서는 신규 적재 0건·중복 40,000건으로 집계됐다. PostgreSQL 통합·DAG 구조를 포함한 테스트 36개도 통과했다. 최초 적재와 재처리를 섞은 기능 확인이므로 성능 개선 수치로 사용하지 않는다. 구현 내용은 [v1 글](v1.md), 측정 원본은 [검증 JSON](../evaluation/v1-smoke.json)에 있다.

### v2 — 실패를 직접 만들고 복구 과정을 검증한다

v1에 재시도 설정이 있다고 해서 실제 장애 복구가 검증된 것은 아니다. v2에서는 실패 지점을 통제해 어느 상태가 남았고, 재시도 후 무엇이 복구됐는지 확인한다.

```text
A 성공 / B 실패 / C 성공
    ├─ 경로 1: 일시 장애 → B 자동 재시도 → 전체 결과 검증
    └─ 경로 2: 재시도 소진 → 실패 보고서·DAG 실패
                               ↓ 운영자가 장애 해제
                           B와 최종 검증만 재실행
                               ↓
                           A·C 실행 횟수 유지 확인
```

주요 장애 지점은 **결과 파일 저장 후 DB 적재 실패**, **DB 커밋 후 완료 기록 전 프로세스 종료**다. 파일과 DB가 하나의 트랜잭션이 아니므로 일부 작업만 끝난 상태에서 다시 실행해도 안전해야 한다.

동시에 잘못된 주문 값, 읽을 수 없는 파일, 동일 주문의 동시 적재, 같은 키의 다른 내용도 확인한다. 입력 자체의 오류와 재시도로 회복할 수 있는 일시 장애는 구분한다. Airflow는 태스크 내부의 마지막 성공 줄부터 이어 실행하지 않으므로, 태스크가 처음부터 다시 실행되는 경우를 검증한다.

**완료 기준:** 실패한 B만 재처리할 수 있고 A·C의 성공 결과와 실행 횟수가 유지된다. 최종 주문 키·내용은 기대값과 일치하며, 복구되지 않은 상태를 DAG 성공으로 표시하지 않는다. 장애 주입 전후의 태스크·파일·DB 기록을 데모로 남긴다.

### v3 — 병렬도를 측정하고 저장 후 불일치를 찾는다

v3에서는 성능 실험과 데이터 정합성 검사를 별도 경로로 진행한다.

```text
경로 1 · 성능 실험
같은 입력·초기 DB·자원 → Pool 1·2·4 반복 실행
    → 전체 시간·처리량·대기 시간·DB 작업 측정
    → 결과 데이터가 같은지 확인 → 적절한 동시 실행 수 판단

경로 2 · 저장 후 정합성 검사
파일 삭제·DB 주문 삭제·금액 변경을 의도적으로 발생
    → 별도 검사 DAG 실행 → 누락·값 불일치 기록
    → 사람이 복구 → 재검사로 해결 여부 확인
```

성능 실험은 조건별로 최소 3회 실행하고, 초기 적재와 중복 재처리를 분리한다. 같은 코드·데이터·파일 분할·자원을 사용하며 동시 실행 수만 바꾼다. 실행 순서와 캐시 조건도 기록한다. 인위적인 대기 시간을 넣어 병렬 처리 효과를 연출하지 않는다.

동시 실행 수가 늘어도 DB 경합이나 스케줄링 비용 때문에 빨라지지 않을 수 있다. 목표는 특정 배수의 개선을 미리 정하는 것이 아니라, **측정으로 병목과 적절한 동시 실행 수를 설명하는 것**이다.

정합성 검사는 총건수만 비교하지 않고 주문 키와 값을 대조한다. 검사 범위를 명시하고 일부 배치만 확인했다면 그 범위의 오류만 해결 상태로 바꾼다. 발견한 데이터를 자동 삭제하거나 수정하는 기능은 포함하지 않는다.

**완료 기준:** 반복 측정 결과와 조건을 공개하고, 저장 후 발생한 불일치를 재현·탐지·해결 확인할 수 있다. 성능 수치와 데이터 정확성 검증을 함께 제시한다.

## 5. 범위는 어디까지 잡을 것인가

첫 시리즈는 가상 쇼핑몰 두 곳의 **신규 확정 주문·원화 정수 금액·파일 배치**에 집중한다. 모든 데이터는 직접 생성하며, 원본 보관과 분석용 개인정보 제외 범위를 구분한다.

실제 쇼핑몰 API 연동, 주문 변경·환불, 실시간 스트리밍, 여러 서버의 분산 처리, 별도 웹 대시보드는 이번 v1~v3의 필수 범위가 아니다. 대화 데이터까지 함께 다루는 범용 ETL 프레임워크로 확장하지 않고, 동일한 주문 파이프라인의 병렬 처리와 복구를 끝까지 검증한다.

## 6. 포트폴리오에는 무엇을 남길 것인가

버전마다 **문제 → 설계 판단 → 구현 흐름 → 재현 가능한 실험 → 결과와 한계**를 연결한다. 사용 기술 목록보다 선택한 이유와 실제로 확인한 동작이 드러나도록 작성한다.

| 자료 | 담을 내용 |
| --- | --- |
| README | 프로젝트 목적·핵심 결과·빠른 실행 방법 |
| v0 글 | 프로젝트 제안과 v1~v3 진행 방향 |
| v1 글 | 파일별 병렬 처리 구조와 실제 적재·재실행 결과 |
| v2 글 | 부분 실패가 남기는 상태와 선택적 복구 과정 |
| v3 글 | 병렬도 비교·병목 분석·정합성 검사 결과 |
| 실행 기록·데모 | 입력 조건, 태스크 상태, DB 결과, 검증 보고서 |

최종적으로는 평가자가 프로젝트를 실행해 **정상 처리 → 특정 파일 실패 → 재처리 → 결과 검증**을 따라갈 수 있어야 한다. 성능 개선이나 복구 보장은 실제 실험이 뒷받침하는 범위에서 설명한다.

현재 구현부터 살펴보려면 [v1 — Airflow로 주문 파일을 병렬 처리하기](v1.md)를, 직접 실행하려면 [실행 안내](usage.md)를 참고하면 된다.
