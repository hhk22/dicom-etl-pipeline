# Airflow ETL v2 — 장애 주입으로 기존 재시도 구조 검증하기

> **v1의 자동 재시도 구조에 장애 주입과 영구 오류 구분을 추가하고, 파일 저장·DB 커밋 직후 실패해도 재시도로 데이터가 유지되는지 검증했다.**

**Python · Apache Airflow · PostgreSQL · Docker Compose**

## 왜 필요한가

v1에서는 주문 파일의 병렬 처리와 같은 입력의 재실행을 확인했다. v2에서는 **파일과 DB 중 한쪽만 저장된 상태에서 멈추면 어떻게 되는가**를 검증했다.

결과 파일을 저장한 뒤 DB 적재가 실패할 수도 있고, DB에는 저장됐지만 로컬 성공 보고서를 쓰기 전에 프로세스가 종료될 수도 있다. 이때 Airflow가 실패한 파일을 처음부터 다시 실행해도 데이터가 유지돼야 한다.

## 실행 흐름 — 기존 동작과 v2의 변경점

### v1·v2 공통: 실패한 B만 자동 재시도

아래는 A·C가 성공하고 B에서 재시도 대상 오류가 발생한 경우의 코드 흐름이다. A·B·C는 설명용 예시이며, 실제 실험 결과는 마지막의 ‘검증 결과와 다음 단계’에 정리했다.

```text
파일 A 성공 / B 실패 / C 성공
    ↓
Airflow가 B만 15초 지연 후 1회 재시도
    ├─ 경로 1: B 성공 → 전체 결과 검증
    └─ 경로 2: B 다시 실패 → 실패 보고서·DAG 실패

A·C는 두 경로 모두 재실행하지 않음
```

**B만 재시도하고 성공한 A·C를 유지하는 동작은 v1부터 있었다.** 재시도 시 B의 파일 처리는 처음부터 실행된다. 일정한 결과 파일 경로와 주문 중복 방지도 두 버전이 공유한다.

### v2 추가: 장애를 재현하고 영구 오류의 재시도를 중단

v2에서는 기존 재시도 경로에 들어갈 장애를 원하는 배치·저장 지점에서 발생시키는 기능을 추가했다. 또한 읽을 수 없는 파일과 해시 불일치는 재시도해도 해결되지 않는 오류로 구분했다.

```text
경로 1: B의 저장 경계에 장애를 한 번 주입 (once)
    → 장애 발생 표시를 남기고 B 실패
    → 기존 Airflow 정책으로 B 재시도
    → 장애 발생 표시가 있으므로 같은 장애는 생략
    → 부분 저장 상태에서 재처리 → 결과 데이터 검증

경로 2: B의 저장 경계에 장애를 매번 주입 (always)
    → B 실패 → 기존 Airflow 정책으로 B 재시도
    → 다시 장애 발생 → 재시도 1회 소진
    → 실패 보고서·DAG 실패 여부 검증

경로 3: B의 파일 파싱 실패·원본 해시 불일치
    → v1: 일반 오류처럼 자동 재시도
    → v2: PermanentBatchError → AirflowFailException
           → 자동 재시도 없이 B 실패 → 최종 검증에서 DAG 실패
```

경로 1·2의 장애 지점은 파일 저장 직후 또는 DB 커밋 직후다. `once`의 표시는 장애 발생 이력을 저장하는 파일이며 주문 파일과는 별개다. `always`는 해당 지점에 도달할 때마다 장애를 발생시키지만, 재시도 횟수는 기존 Airflow 설정인 1회로 제한된다. 기본값 `fault_point=none`에서는 의도한 장애를 발생시키지 않는다. 경로 3은 장애 주입 설정과 관계없이 실제 파일 오류에 적용한다.

| 비교 항목 | v1 | v2 |
| --- | --- | --- |
| B만 자동 재시도·성공한 A·C 유지 | 이미 구현 | 기존 동작 유지 |
| 일정한 파일 경로·주문 중복 방지 | 이미 구현 | 기존 구현 사용 |
| 저장 지점·대상 배치·횟수를 지정한 장애 주입 | 없음 | 추가 |
| 파일 파싱 실패·해시 불일치 | 자동 재시도 대상 | 영구 오류로 구분해 재시도 중단 |
| 실제 DAG 검증의 중심 | 정상 병렬 적재·같은 입력의 재실행 | 부분 저장 후 재시도 시 데이터 유지·재시도 소진 시 실패 판정 |

## 검증 결과와 다음 단계

기존 DAG 실험에서 파일 저장·DB 커밋 직후 장애를 주입했다. `once`는 자동 재시도로 성공해 **고유 주문 4,000건을 중복 삽입 없이 유지**했고, 성공한 나머지 파일은 재실행하지 않았다. `always`는 재시도 소진 후 DAG 실패로 끝났다.

검증은 태스크 내부 오류와 프로세스 종료를 대상으로 했으며, DB 서버 전체 장애·디스크 손상은 포함하지 않았다. 파일과 DB의 부분 저장은 재처리로 맞추는 구조다. 위 결과는 코드 정리 전 실행 기록이며, 최신 테스트 결과는 [실행 안내](usage.md#테스트와-현재-검증-범위)에 구분했다.

v3에서는 같은 조건에서 병렬도별 성능을 비교하고, 저장 후 불일치를 찾는 별도 정합성 검사를 추가한다.
