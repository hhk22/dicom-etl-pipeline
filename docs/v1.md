# Commerce ETL v1 — 주문 파일 4만 건을 병렬 처리하고 검증하기

> **서로 다른 주문 파일을 공통 형식으로 변환하고, 다시 실행해도 주문이 중복 저장되지 않는 배치 파이프라인을 구현했다.**

**Python · Apache Airflow · PostgreSQL · Docker Compose**

| 처리 규모 | 병렬 실행 | 재실행 결과 |
| --- | --- | --- |
| **8개 파일 · 40,000건** | 동시 처리 **1·2·4개 확인** | 신규 추가 **0건**, 기존 주문 유지 |

## 왜 만들었나

의료영상 ETL 실무에서 다룬 **입력 형식 차이, 개인정보 처리, 재처리 시 중복 문제**를 가상 쇼핑몰 주문으로 재구성했다. 데이터와 코드는 공개 포트폴리오용으로 별도 구성했다.

v1의 목표는 여러 파일을 병렬로 처리하면서 **무엇이 저장됐고, 무엇이 중복되거나 잘못됐는지 확인할 수 있는 구조**를 만드는 것이다.

## 어떻게 동작하나

```text
쇼핑몰 A 형식 CSV + 쇼핑몰 B 형식 JSON
    ↓
처리할 파일 목록 확정 · 원본 보관
    ↓ Airflow에서 파일별 병렬 처리
    ├─ 파일 A → 검증·형식 통일·고객 ID 가명 처리 → 저장
    ├─ 파일 B → 검증·형식 통일·고객 ID 가명 처리 → 저장
    └─ 파일 C → 검증·형식 통일·고객 ID 가명 처리 → 저장
    ↓
처리 기록 · 결과 파일 · DB 주문 대조
    ↓
검증 결과에 따라 실행 성공/실패 판정
```

입력은 직접 생성한 합성 파일이다. 운영자가 실행하면 이후 과정은 자동으로 진행된다. Docker Compose로 재현할 수 있으며, 단일 머신에서 여러 프로세스가 동작한다.

## 핵심 설계 세 가지

### 1. 파일별 작업 생성과 동시 실행 제한

Airflow의 **Dynamic Task Mapping**으로 파일 수만큼 처리 작업을 만들고, **Pool**로 동시에 실행할 작업 수를 제한했다. 예를 들어 파일이 8개이고 동시 실행 한도가 4개라면, 최대 4개가 실행되고 나머지는 자리가 날 때까지 대기한다.

파일 하나를 작업 단위로 선택해 파일별 상태를 추적할 수 있게 했다. Airflow에는 실행 순서와 재시도를 맡기고, 데이터 변환과 저장 결과 검증은 Python으로 구현했다.

### 2. 같은 주문의 중복과 내용 충돌 구분

쇼핑몰마다 다른 필드명·시간 표현을 공통 주문 형식으로 통일했다. 고객 ID는 가명 토큰으로 바꾸고, 이름·이메일·주소는 분석 결과에서 제외했다. 원본은 별도로 보관한다.

저장 시에는 쇼핑몰과 주문 ID로 주문을 구분한다.

| 입력 상황 | 처리 방식 |
| --- | --- |
| 처음 들어온 주문 | 신규 저장 |
| 같은 주문, 같은 내용 | 중복으로 기록하고 추가 저장 생략 |
| 같은 주문, 다른 내용 | 기존 값 유지 · 충돌 기록 · 최종 검증 실패 |

예를 들어 이미 저장된 10,000원 주문이 12,000원으로 다시 들어오면, 자동으로 덮어쓰지 않고 충돌로 남긴다. v1은 신규 확정 주문을 대상으로 하며 주문 변경·환불은 범위에서 제외했다.

### 3. 작업 종료 후 데이터까지 검증

마지막 단계에서는 **이번 실행의 처리 요약·행별 기록을 정규화한 파일과 DB 주문에 대조**한다. 건수나 내용이 다르거나 잘못된 입력·충돌이 있으면 전체 실행을 실패로 표시한다.

원본을 다시 변환하는 검사는 아니며, 변환 규칙 자체는 별도 테스트로 확인한다.

## 실행 결과

**8개 파일·40,000건**을 처리하고 같은 입력을 두 번 더 실행했다. 동시 실행 제한이 적용되는지 확인하기 위해, 실행할 때마다 Pool 슬롯을 **4 → 1 → 2개**로 직접 변경했다.

| 실행 | 지정한 Pool 슬롯 | 실제 최대 동시 처리 | 신규 저장 | 중복 판정 |
| --- | ---: | ---: | ---: | ---: |
| 최초 적재 | 4개 | 4개 | 40,000건 | 0건 |
| 재실행 1 | 1개 | 1개 | 0건 | 40,000건 |
| 재실행 2 | 2개 | 2개 | 0건 | 40,000건 |

**동시 처리 수 1·2·4를 확인했고, 재실행 후에도 고유 주문 40,000건과 내용·금액이 유지됐다.** 별도로 DB 통합·DAG 구조 검사를 포함한 테스트 36개를 통과했다.

최초 적재와 재처리는 작업량이 달라, 이 결과를 속도 개선 수치로 비교하지 않았다.
